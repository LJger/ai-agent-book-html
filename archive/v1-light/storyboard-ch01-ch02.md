## 一、总体约定

### 内容深度

- **与原书一致**：不为零基础观众降级简化，也不超出原书范围。旁白取自原书正文，只压缩措辞，不删减论点。
- 每个场景标注对应的原书小节和图号，播放时显示在旁白上方，方便对照原文。
- 原书配图与正文不一致时，**以正文为准**，并在本稿"差异记录"中登记。

### 结构与节奏

- 层级：**章 → 场景 → 步骤**。每一步 = 一段旁白 + 一段动画。
- 画面跟着旁白走：场景用 `cue('某个词')` 取得"读者读到这个词的时刻"，在那一刻让对应元素出场。
- 阅读速度按 **5 字/秒** 估算；每步时长 = max(动画时长 + 1.5 秒, 旁白阅读时间)。速度常量在 `web/js/core/player.js` 顶部。
- 默认连续播放；可暂停、上一步/下一步（暂停时直接显示该步完成后的画面）、点击或拖动进度条、0.5×–2× 调速。

## 四、MVP 待制作场景分镜

### 场景 1-6 上下文：Agent 的眼睛

原书位置：第一章「上下文：Agent 的眼睛」、实验 1-1、图1-3。

**第 1 步**
- 画面：桌面上摊开四份资料（任务说明、参考手册、沟通记录、最新数据），镜头收拢成一个竖直的"上下文窗口"框。
- 旁白：上下文是 Agent 在每个决策点能看到的全部信息。就像一个人做决策时需要看到桌上摊开的所有资料——任务说明、参考手册、之前的沟通记录、最新的数据——上下文窗口就是 Agent 的"视野"。

**第 2 步**
- 画面：窗口内自上而下依次落入五个色块：系统提示词、工具定义、用户消息、模型回复、工具执行结果。
- 旁白：从 API 的视角看，每次调用 LLM 时的上下文由五个部分构成：系统提示词、工具定义、用户消息、模型回复和工具执行结果。

**第 3 步**
- 画面：聚焦"系统提示词"，标签"岗位说明书"，内嵌"用户记忆（第三章）""动态注入的环境状态"两个小块；聚焦"工具定义"，展开为名称 / 功能描述 / 参数格式三栏。
- 旁白：系统提示词由开发者编写，在整个对话中保持不变，相当于 Agent 的"岗位说明书"，定义它的身份、权限和行为准则；其中还包含跨会话保存的用户记忆和动态注入的环境状态。工具定义声明可用工具的名称、功能描述和参数格式——没有它，Agent 就无法识别和调用任何工具。

**第 4 步**
- 画面："用户消息"旁出现一个"RAG 检索的外部知识"小块；"模型回复"展开成 reasoning / content / tool_calls 三个槽位，先点亮 reasoning + tool_calls（决定调用工具），再点亮 reasoning + content（最终回答）。
- 旁白：用户消息中还可能包含通过 RAG 动态检索引入的外部知识。模型回复最多包含三部分：思考过程 reasoning、给用户的文本 content、工具调用请求 tool_calls。三者不一定同时出现：决定调用工具时通常只有 reasoning 和 tool_calls，给出最终回答时通常只有 reasoning 和 content。

**第 5 步**
- 画面：工具执行结果块出现，箭头指向"下一步思考"。两道括号：上两块"静态前缀（保持不变）"，下三块"动态消息历史（随交互增长）"；下半部分一轮轮追加新块，上半部分不动。角落小注："2026 年起，工具的完整 schema 也可按需加载到上下文末尾（第二、四章）"。
- 旁白：工具执行结果是 Agent 下一步思考的直接依据。前两项——系统提示词和工具定义——构成保持不变的静态前缀；后三项是随交互不断增长的动态消息历史。五个部分共同构成了 LLM 每次推理时的上下文。

**第 6 步**
- 画面：图1-3 的消融设计：五列对照——完整基线，以及缺工具定义 / 缺工具执行结果 / 缺思考过程 / 缺历史消息；系统提示词一列灰掉，注明"不参与消融"。
- 旁白：怎样验证每个组件是否不可或缺？最直接的方法是消融实验：像医生逐一排除病因，每次去掉一个组件，看系统是否还正常。实验 1-1 设置了一组完整基线和四组各缺一个组件的对照；系统提示词是 Agent 的基本身份定义，没有它连角色认知都没有，因此不参与消融。

**第 7 步**
- 画面："缺工具定义"一列放大：两份答案并排，排版一样、语气同样笃定；翻到背面，一份写着"来自参数记忆"，一份写着"来自真实观测"。底部大字："给出了回答 ≠ 完成了任务"。
- 旁白：去掉工具定义，Agent 失去行动能力，却并不沉默：模型照样给出一份格式工整、语气笃定的答案，数据却来自参数记忆，排版与真正基于观测的答案一模一样。是坦白拒绝还是就地编造，主要取决于模型自身的幻觉率与诚实度；提示词里"不得自行估计"这类约束只能降低编造的概率，并不能消除。

**第 8 步**
- 画面：三列依次演示——缺工具执行结果：迭代计数器一路涨到上限，红字"迭代预算耗尽"；缺思考过程：reasoning 块淡出，工具结果块还在，注"可从工具结果重建"；缺历史消息：同一个工具调用重复出现。
- 旁白：缺少工具执行结果，Agent 会"盲目"执行，反复重试直到耗尽迭代预算——工具结果是闭环控制的关键。思考过程记录"为什么这么做"，工具结果记录"发生了什么"；当前者可以从后者重建时，把它从历史中丢掉几乎没有代价。历史消息则防止冗余操作，避免重复犯同样的错误。

**第 9 步**
- 画面：核心洞察卡："上下文决定 Agent 能看到什么，Agent 只能基于它看到的信息做决策"；下方两条小字：组件不等价，标准是信息能否从别处重建；模型迭代很快，结论要在新模型上重新实测。
- 旁白：这个实验的核心洞察是：上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。但组件并不等价，衡量标准是它承载的信息能否从别处重建；模型迭代很快，同一个消融换到新模型上完全可能得出不同结论。对工程实践更重要的是：上下文残缺时，典型的失败不是报错退出，而是一个看上去毫无破绽的答案。

### 场景 1-7 ReAct 循环与轨迹

原书位置：第一章「ReAct 循环」前半、图1-4、最小运行骨架伪代码。

**第 1 步**
- 画面：三节点循环"思考 → 行动 → 观察"；标题 ReAct = Reasoning + Acting。
- 旁白：ReAct 循环把 LLM、上下文和工具串联起来。名字只体现了思考（Reasoning）和行动（Acting），实际循环却有三个环节：模型先思考当前应该做什么，然后调用工具行动，再观察工具返回的结果并继续思考下一步。"想→做→看"不断重复，直到任务完成。

**第 2 步**
- 画面：左侧竖条"上下文"：顶部灰色"静态前缀：系统提示词 + 工具定义"，下方空白区标"轨迹 trajectory"。公式：上下文 = 静态前缀 + 轨迹。
- 旁白：轨迹是 Agent 在执行任务过程中不断积累的消息历史：用户消息、模型回复（包括思考过程和工具调用）、工具执行结果。每次调用 LLM 时，它接收的完整上下文由静态前缀和轨迹两部分组成：Agent 的上下文 = 静态前缀 + 轨迹。

**第 3 步**
- 画面：user 消息落入轨迹："根据公司季度收入：Q1 2.5M 美元，Q2 2.1M 欧元，Q3 1.8M 英镑，Q4 380M 日元，计算公司年度总收入和季度平均收入"。
- 旁白：来看一个多币种收入汇总的例子：用户给出四个季度、四种货币的收入，要求计算公司年度总收入和季度平均收入。

**第 4 步**
- 画面：第 1 次迭代：上下文整体流入中间的 Model；Model 吐出 assistant 块：reasoning"需要将所有货币转换为 USD…"，content 为空，tool_calls 并列三个 convert_currency（EUR / GBP / JPY）。
- 旁白：第一次迭代：LLM 看到静态前缀和当前轨迹，判断需要先把所有货币换算成美元。它没有直接回复用户，而是一次发出三个 convert_currency 工具调用，分别换算欧元、英镑和日元。

**第 5 步**
- 画面：Harness 校验（✓）→ Environment 执行，三条 tool 结果追加到轨迹末尾：EUR→USD 2282608.7、GBP→USD 2278481.01、JPY→USD 2541806.02。
- 旁白：Agent 框架校验并执行这三个调用，把结果逐条追加到轨迹末尾。Model 只负责决定下一步；组装上下文、校验并执行工具的是 Harness；产生真实状态变化和观察的是 Environment。

**第 6 步**
- 画面：第 2 次迭代：reasoning"已获得转换结果，现在需要汇总计算…"→ code_interpreter("total = 2500000 + 2282608.7 + …")；结果"Total: $9,602,895.73, Average: $2,400,723.93"。
- 旁白：第二次迭代：LLM 看到包括工具结果在内的完整轨迹，调用代码解释器做汇总，得到年度总收入 9,602,895.73 美元、季度平均 2,400,723.93 美元。

**第 7 步**
- 画面：第 3 次迭代：没有 tool_calls，只有 reasoning + content"FINAL ANSWER: 总收入 $9,602,895.73…"；循环出口亮起；计数牌"3 次迭代 · 4 次工具调用"。
- 旁白：第三次迭代：所有计算已经完成，模型不再调用工具，直接给出最终答案。整个过程只用了 3 次迭代、4 次工具调用。注意，轨迹中没有系统提示词和工具定义——它们作为静态前缀，在每次调用时自动拼接在轨迹前面。

**第 8 步**
- 画面：右侧出现最小运行骨架伪代码；重放一遍循环，伪代码逐行高亮与画面同步。三个角色标签：Model / Harness / Environment。
- 旁白：这就是最小运行骨架：每轮把静态前缀和轨迹拼成上下文交给 Model；Model 的决策追加进轨迹；没有工具调用就返回答案，否则由 Harness 逐个校验调用、交给 Environment 执行，再把观察追加进轨迹。互不依赖的调用可以并行执行。

**第 9 步**
- 画面：轨迹复制成三份，流向调试、知识库、强化学习训练三个去处。
- 旁白：在这种最基本的设计中，上下文不断追加：每次调用都能看到完整轨迹，模型清楚任务进行到了哪一步、尝试过什么、得到了什么结果。结构化的轨迹也易于解释和调试；分析大量轨迹可以改进决策路径和工具设计，轨迹还可以沉淀进知识库，或用于强化学习训练更好的模型，形成从经验中学习的闭环。

### 场景 2-2 API 的上下文结构

原书位置：第二章「Agent 如何调用大模型」「消息的四种角色」「单轮对话」、图2-2。

**第 1 步**
- 画面：问题"上下文在技术上以什么形式送给大模型？"→ 一个请求信封，内含 messages 列表。
- 旁白：这些上下文信息在技术上以什么形式送给大模型？以 OpenAI 的 Chat Completions API 为例（Anthropic、Google 等厂商的结构大同小异），API 的核心是一个消息列表 messages，列表中每条消息都有一个角色标识，模型根据角色理解每条消息的含义和来源。

**第 2 步**
- 画面：四张角色卡依次出现：system、user、assistant、tool，各带一行说明。
- 旁白：system 是系统提示词，由开发者编写，模型将其视为最高优先级的指令，通常只有一条并放在最前；user 是终端用户的输入；assistant 是模型之前的回复，包括文本和工具调用请求，放回列表让模型"记住"自己说过什么；tool 是 Agent 框架执行工具后送回的结果，通过 tool_call_id 与对应的调用请求关联。

**第 3 步**
- 画面：tools 字段出现在 messages 之外（虚线框注"请求的独立字段，不是消息"）；五条连线把"四种角色 + tools"对应到第一章的五个上下文组成部分。
- 旁白：工具定义 tools 是请求的独立字段，而不是一种消息角色。因此"四种消息角色 + tools 字段"恰好覆盖第一章所说的五个上下文组成部分——这是同一个请求结构的两种分类方式。

**第 4 步**
- 画面：单轮调用：请求 JSON 逐行出现（model: Qwen3-0.6B；system；user "Hello, who are you?"）→ 模型 → 响应 assistant "Hi! I'm a coding assistant…"。
- 旁白：先看最简单的单轮调用：用户问"Hello, who are you?"。请求只包含两条消息：开发者写的 system 和用户的 user；模型返回一条 assistant 消息作为回复。

**第 5 步**
- 画面：模型盒子上的"记忆"格始终为空；第二个请求信封必须重新装入全部内容。大字：每次调用都是无状态的。
- 旁白：这就是大模型 API 最基本的交互模式：每次调用都是无状态的，模型需要的所有信息都必须在请求的消息列表中完整提供。

### 场景 2-3 核心循环：两次 API 调用

原书位置：第二章「带工具调用的多轮交互」「用代码实现 Agent 的核心循环」「从 API 视角看上下文的构成」、图2-3、图2-4。

**第 1 步**
- 画面：用户提问"What's the current time and weather in Vancouver?"；模型旁两个问号："现在"是什么时候？天气呢？
- 旁白：当用户问"What's the current time and weather in Vancouver?"时，模型无法凭自身知识回答：它不知道"现在"是什么时候，更不知道天气，需要调用外部工具。

**第 2 步**
- 画面：第 1 次请求：system + user + tools（get_current_time、get_weather）；tools 旁注"静态元数据，与这次问了什么无关；真实 Agent 往往挂几十个工具"。
- 旁白：第一次 API 调用，Agent 框架发送 system、user 和 tools。这份 tools 清单是开发者事先注册好的静态元数据，与用户这次问了什么无关。并不是 Agent 先把问题拆成"查时间"和"查天气"再生成工具描述——拆解发生在模型一侧。

**第 3 步**
- 画面：响应：content: null，tool_calls 两条：call_abc123 get_current_time {timezone: "America/Vancouver"}、call_def456 get_weather {city: "Vancouver", unit: "celsius"}；两条之间标注"无依赖 → 可并行"。
- 旁白：模型没有直接回答，而是返回两个工具调用请求：它判断时间和天气需要通过工具获取，而且两者之间没有依赖，可以并行调用。关键在于：模型只是发出调用请求，真正执行工具的是 Agent 框架。

**第 4 步**
- 画面：框架并行执行两个工具（两条进度条同时走完），生成两条 tool 消息，tool_call_id 连线回各自的调用。旁注：若后一个工具的参数依赖前一个结果，只能在下一轮串行。
- 旁白：Agent 框架实际执行这两个工具，把结果包装成两条 tool 消息，各自通过 tool_call_id 关联对应的调用。如果后一个工具的参数必须来自前一个工具的结果，模型就要在后续一轮再发起调用，两个工具只能串行执行。

**第 5 步**
- 画面：第 2 次请求：完整历史依次飞入信封——system、user（"与第 1 次相同"）、assistant（"原样放回"）、tool ×2（"新增"）+ tools；三处关键细节编号高亮。
- 旁白：第二次请求包含了第一次的全部对话历史——这就是"无状态"：模型不会记住上一次对话，框架必须每次把完整历史送回去。第一次的 assistant 消息被原样放回，让模型看到自己之前的决策；tool 消息通过 tool_call_id 让模型知道哪个结果对应哪个调用。

**第 6 步**
- 画面：最终回复（无 tool_calls）："It's currently 5:18 AM on Saturday, September 13, 2025 in Vancouver… 13.2°C with clear skies…"；循环图标收束为"停止"。随后追问"那东京呢？"追加到末尾，循环再次启动。
- 旁白：这一次模型没有返回 tool_calls，而是直接给出文本回复，Agent 停止执行。"请求→工具调用→执行→送回结果→再请求"的循环，就是第一章 ReAct 循环在 API 层面的实现。如果用户追问"那东京呢？"，框架把追问追加到历史末尾，再发起一次调用。

**第 7 步**
- 画面：左侧 while 循环代码，右侧 messages 列表；代码逐行高亮的同时列表增长：初始 2 条 → 第 1 次调用后 5 条 → 第 2 次调用后 6 条。
- 旁白：用代码实现，核心只是一个 while 循环和一个判断：模型返回了 tool_calls 就执行工具并继续循环，没有就输出结果并退出。整个过程中 messages 列表不断增长。Agent 框架的核心工作，就是管理这个 messages 列表——在合适的时机往里追加消息，再把整个列表送给模型。

**第 8 步**
- 画面：图2-4：上半部分（System Prompt + Tool Definitions）冻结为灰色，下半部分（轨迹）持续增长；两侧标注"前面不能动""后面可以压缩"。
- 旁白：从 API 视角看：上半部分的系统提示词和工具定义在整个对话中保持不变，下半部分的对话历史——也就是轨迹——随交互不断增长。这个"静态前缀 + 轨迹"的结构，是后面 KV Cache 优化和上下文压缩的基础：理解了它，就能理解为什么"前面不能动、后面可以压缩"。

### 场景 2-5 KV Cache 的直觉与时间戳事故

原书位置：第二章「KV Cache 友好的上下文设计」开头至「技术门槛提示」。

**第 1 步**
- 画面：一行 token 方块；每生成一个新 token，一束"回看"的光扫过前面所有 token；中间结果被存进"缓存抽屉"，下一轮只计算新增的方块。
- 旁白：先建立 KV Cache 的直觉：模型每生成一个 token，都要回头看一遍前文所有 token 的中间计算结果。如果每轮都从头算，开销会随上下文长度爆炸式增长。KV Cache 把前文的中间结果缓存下来，下一轮只计算新增 token 的部分——前提是要复用的 token 前缀保持不变：从首个不同的 token 起，后面的状态都要重新计算。

**第 2 步**
- 画面：同一个缓存抽屉被多个请求共用，标签"Prompt Cache（跨请求）"。
- 旁白：在 API 服务商的语境下，跨请求的缓存命中叫 Prompt Cache——它是构建在推理引擎 KV Cache 之上的跨请求缓存。两个层级的完整辨析放在后面的场景里。

**第 3 步**
- 画面：客服 Agent 仪表盘：每天 10 万次对话、首 token 延迟 0.5 秒、账单平稳；工程师在系统提示词里加了一行 `Current time: {{now}}`；第二天告警：延迟 3–5 秒，月账单几乎翻倍。
- 旁白：某团队的客服 Agent 每天处理 10 万次对话，一切正常。某天工程师为了让 Agent"知道"当前时间，在系统提示词里加了一行 Current time: {{now}}。第二天监控告警：所有对话的首 token 延迟从 0.5 秒涨到 3–5 秒，月度推理账单几乎翻了一倍。代码看起来完全没问题，模型也没换。

**第 4 步**
- 画面：两次请求的 token 序列上下对齐，从时间戳所在位置开始，后面全部变红。
- 旁白：问题出在那一行时间戳：它让每次请求的 token 序列从时间戳所在位置开始不同，该位置及其后的 KV 状态都无法复用。系统提示词位于上下文前部，模型往往要重新计算其后大部分输入 token 的键值对。一行看似无害的代码，可能让整条推理链路慢一个量级。

**第 5 步**
- 画面：三条核心结论依次落下：① 系统提示词和工具定义一旦确定就不要改；② 动态信息永远追加到末尾；③ 使用标准 API 格式，不要自行拼接消息。
- 旁白：由此得到三条核心结论：一，系统提示词和工具定义一旦确定就不要改，哪怕多一个空格也可能改变 token 序列；二，时间戳、用户状态等动态信息，永远作为新消息追加到对话末尾；三，使用标准 API 格式，不要自行拼接"USER: … ASSISTANT: …"——它偏离了模型训练时的格式，会削弱多步思考能力；缓存只认字节序列，拼接方式不稳定时同样会失效。

**第 6 步（交互）**
- 画面：两个开关——"时间写进系统提示词" / "时间作为新消息追加到末尾"；切换时缓存命中区域和费用条实时变化。
- 旁白：你可以亲手试一试：把时间写进系统提示词，缓存从变动点起全部失效；把它作为新消息追加到末尾，前面所有已缓存的内容都不受影响。

### 场景 2-8 KV Cache 的原理与约束

原书位置：第二章「KV Cache 的原理与约束」、图2-10。

**第 1 步**
- 画面：第 6 轮对话，上下文 2000 token；无缓存时每生成一个新 token，2000 个方块全部重新闪烁计算，前 5 轮的方块明明没变。
- 旁白：设想 Agent 正在进行第 6 轮对话，上下文已累积 2000 个 token。没有缓存时，模型每生成一个新 token，都要重新计算这 2000 个 token 的 K、V 向量——前 5 轮的内容完全没变，也要像第 1 轮那样从头算，而且前缀更长、代价更大。无缓存时，prefill 阶段的注意力计算量随上下文长度平方级增长。

**第 2 步**
- 画面：图2-10 三行：请求 1 建立缓存；请求 2 前缀不变 → 命中 ✓；请求 3 把时间戳放在最前 → 失效 ✗，其后全部重算。下方对比：首 token 延迟约 0.5 秒 vs 3–5 秒（示意值）；成本：仅新 token 计费 vs 变动点后全部重新计费。
- 旁白：图中三次请求说明了跨请求的前缀复用：请求 1 建立缓存；请求 2 前缀不变，直接命中；请求 3 把动态时间戳放在系统提示词最前面，变动点之后的全部 token 都要重新计算和计费。图中的延迟是示意值，随模型、硬件和部署方式而变。

**第 3 步**
- 画面：[A, B, C, D] 四个 token；D 发出 Query，与 A–D 的 Key 逐一点积打分（分数条），再对 Value 加权求和，得到 D 位置的输出 → 预测出 E；E 的 Q/K/V 用虚线框表示"尚未计算"。
- 旁白：用一个简单例子理解：上下文有 [A, B, C, D]，模型正要生成第 5 个 token E。这一步的 Query 来自最后一个已知 token D，它与 A、B、C、D 的 Key 做点积计算匹配度，再按匹配度对它们的 Value 加权求和，得到 D 位置的输出，模型用它预测出 E。E 自己的 Q、K、V 要等它被采样出来、送回模型之后才会计算。

**第 4 步**
- 画面：不使用缓存：生成 E 时重算 4 组 K、V；生成第 6 个时重算 5 组……叠成一个越来越宽的阶梯，右侧标注 ∝ N²。
- 旁白：不使用 KV Cache 时，每生成一个新 token 都要把整个前缀从头前向计算一遍：生成 E 时要算 4 组 K、V，生成第 6 个 token 时要连 E 一起算 5 组……前缀长到 N 个 token 时要算 N 组，累计计算量与 N² 成正比。

**第 5 步**
- 画面：使用缓存：每个 token 的 K、V 只在首次进入上下文时计算一次并存入缓存格；生成 E 时直接取用；E 被采样后计算自己的 K、V 并追加，缓存长到 5 组。旁注：每步注意力仍要遍历全部缓存。
- 旁白：使用 KV Cache 时，每个 token 的 K、V 只在它第一次进入上下文时计算一次，之后一直留在缓存里。但要注意，KV Cache 省去的是历史 token 的 K、V 重算；每个新 token 的注意力计算仍要遍历全部缓存，计算量随上下文长度线性增长——这正是长上下文解码越来越慢、KV Cache 的显存与带宽成为推理瓶颈的原因。

**第 6 步**
- 画面：层 × token 网格（数十层串联）；改动第 k 个 token：k 之前的列保持绿色（可复用），从第 k 列起所有层逐层变红（需重算）。
- 旁白：为什么修改前缀会让变动点之后的缓存失效？大模型由数十到上百层 Transformer 串联而成，每一层都独立生成自己的 K、V 缓存，处理每个词时都综合了它前面所有词的信息。如果第 k 个 token 变了，k 之前的状态不受影响，但从 k 开始的表示会逐层受到影响——缓存只能保留到首个不同 token 之前。

**第 7 步（交互）**
- 画面：拖动"变动点"从末尾移到开头，红色重算区域随之扩大，右侧费用与延迟条同步变长；结论条"系统提示词一旦定下来就不要改"。
- 旁白：代价取决于改动位置：变动点越靠前，需要重新计算和计费的 token 越多，延迟影响通常也越大，本章实验中实测可达数倍。这就是为什么系统提示词一旦定下来就不要改。
