在动手调算法之前，先问自己——我的仿真环境，真的像真实世界吗？

练习场与考场不同，策略就会失效

示意
仿真成功率 —上线成功率 —
01
环境一旦失真，策略就会失效学到只在仿真里管用的“应试策略”——RL 项目最常见的失败方式
02
高保真环境常常比训练本身更贵、更难真实 API 有速率限制、会封号、有副作用：先建稳定、可控、可重放的“影子世界”
03
环境的另一半是奖励函数不仅模拟“世界怎么变”，还要判定“做得好不好”

这个问题的答案，比选 PPO 还是 GRPO 重要得多

第八章 ·「RL 环境：从评估到仿真」「环境：模型练习的场地」

造不出环境，就让模型扮演环境

示意
学生 query“2024 年奥运会在哪里举办”
当前状态 sAgent 动作 a经验模型逐步推理状态转移 s′ + 反馈 r

不访问真实环境，批量合成 rollout 用于在线 RL；用户模拟器（τ-bench）同理：既能当考场，也能当练习场

风险

模拟器的世界知识就是训练的天花板，系统性偏差会被策略照单全收：模拟客服更有耐心、模拟搜索从不返回垃圾 → 策略只在“模型扮演的世界”里成立；RL 还会主动利用模拟器漏洞

稳妥做法：混合
模型模拟（大部分交互量）真实交互
并用真实交互定期校准模拟器偏差
第八章 ·「造不出环境怎么办：让模型扮演环境」

共享生成器与验证代码，不共享同一批任务

训练任务同一个任务生成器 · 同一套验证代码
评估任务不重叠的一批；测试用例、隐藏状态、参考解法留在验证器一侧
先小规模，再扩大采样

先用少量 rollout 检查任务是否可完成、验证器是否能区分对错——验证器有系统性偏差，RL 只会更快地利用它（SWE-Gym、τ²-bench、AndroidWorld）

示意确定性验证器“便宜”≠ 没有成本

Lean kernel、测试运行器、容器执行：CPU 验证可能远慢于 GPU 生成
