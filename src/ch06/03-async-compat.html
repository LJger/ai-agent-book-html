兼容同步格式：只在打断时才修补轨迹

场景

Agent 正在帮用户起草邮件，search_contacts 还没返回，用户突然说：“等一下，先帮我查一下明天的天气。”如果接口要求未完成的工具调用先获得对应结果，Agent 就无法带着悬空调用处理这条新消息。

这个限制来自所选协议与模型组合，并非所有 LLM 都必须遵循的规律

    API 已完成的 assistant 消息和工具调用项立即写入；reasoning 状态按提供商续接协议保留，不自行拼接不可见的思考文本

  2. 2
    规则 2 · 完成才记

    工具调用完成时才记录 tool result，执行中的轨迹处于“部分完成”状态

  3. 3
    规则 3 · 打断用占位符

    为未完成的工具生成占位符响应，追加打断事件，重新调用 LLM——assistant message 仍有配对的 tool result

  4. 4
    规则 4 · 无续接接口就取消生成

    保留已确认完成的消息和工具状态，追加新事件后重新请求；半截输出或隐藏推理不能当合法前缀任意回灌

  5. 5
    规则 5 · 非打断事件排队

    进入队列等待批处理，当前周期完成后才一次性追加

核心思想：在没有打断发生的常态下，让 LLM 看到标准的同步轨迹，只在打断时才插入占位符来修复格式

原生异步：模型理解等待与中途变化
任务在后台运行明确记录“尚未完成”status: running
运行时接入新事件决定排队、打断或并行处理排队打断并行
模型继续处理任务仍按同步交互方式接收信息收到的是同步格式的轨迹
发起耗时查询例如：查询会议场地lookup_venues
等待期间继续工作例如：整理议程与准备清单议程 ✓准备清单 ✓
结果到达后作出决策依据真实信息比较场地按全部约束比较场地
用户中途补充要求例如：预算与人数变化预算减少了参会人数变了
保留已完成的工作将新要求纳入当前任务议程、清单不必重做
调整后续行动综合已有信息与全部更新新约束进入后续计划
模型理解变化、调整计划；运行时管理工具执行、任务状态与事件来源能接收异步消息，还需要能正确恢复任务并控制实际动作。
Async tool calling异步工具调用将“发起行动”和“获得结果”分开。

发起耗时查询后，可以继续推理、调用其他工具，处理不依赖结果的部分；必须依据结果的决策，留到结果到达之后

Mid-turn steering回合中途引导让用户可以在任务进行中修正方向。

系统保留已完成的工作，把新约束带入后续处理；接收更新与作出调整之间仍可能有延迟，但用户不必等一整轮回答结束

边界
  • 修改计划不等于停止正在运行的工具，更不会自动撤销已经发生的动作
  • 并非所有模型都具备原生异步能力：按支持范围选择原生交互或兼容方案
