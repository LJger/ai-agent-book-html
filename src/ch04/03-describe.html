描述决定模型怎么选、怎么传；保真决定它看到的是不是真相
工具描述的质量直接决定了 Agent 使用工具的准确性。

说清什么时候用，也说清不能做什么

边界往往比能力更重要

清晰列出工具的边界条件——做不到什么、不接受什么输入——往往比描述能力本身更重要

调试原则

频繁选错工具时，优先检查工具描述；修正描述的投入产出比，通常远高于换一个更强的模型

同样适用于 Skill

不管工具用何种表达方式，都需要清晰的描述文档

第四章 ·「工具描述的艺术」

把描述写到 Agent 可以直接套用

示意
抽象规范
timestamp：RFC3339 格式 phone：使用 E.164 格式
具体例子
timestamp：RFC3339 格式，例如 2024-03-15T14:30:00Z phone：电话号码，使用 E.164 格式（国家代码+号码，无空格或特殊字符），例如 +8613888888888（中国）或 +12025551234（美国）
只说能做什么
web_search：搜索网页 fetch_page：读取网页
加上返回值与代价
web_search：搜索网页。返回 JSON 数组，每个元素包含 title、url、snippet 三个字段 fetch_page：读取网页。此工具需要下载完整网页，大型网站可能需要 5-10 秒；如果只需要元信息，请考虑使用 get_page_metadata
JSON Schema 只有类型
list_events start_time: integer 秒？毫秒？ filters: object 条件怎么嵌套？
附带真实调用示例
示例 1：list_events(start_time=1710513000, filters={"type": "meeting"}) 示例 2：list_events(start_time=1710513000, filters={"all": [{"type": "meeting"}, {"owner": "me"}]})
复杂任务里，留给“确认格式”的注意力很少
同时处理多个工具从历史轨迹提取信息权衡多个决策格式
没有例子2024/3/15 14:30
照着例子2024-03-15T14:30:00Z

具体例子让 Agent 可以直接套用，无需额外的思考步骤

知道代价，才能规划调用顺序
不知道代价
fetch_pagefetch_pagefetch_page
注明了代价
metametametafetch_page

说清返回字段，能减少后续解析时出错；注明“5-10 秒”，LLM 会先用 get_page_metadata 筛一遍

示例传达 schema 表达不了的隐式约定
72%

在一些基准上，工具调用准确率可从约 72% 提升到 90%具体数值因任务而异（原书）

第四章 ·「参数传递的保真性」

工具不能背着模型改输入

模型以为
工具层悄悄改动
实际发生示意
模型感知到的世界≠工具操作的世界
不能存在系统性的偏差：参数传递必须透明。确需规范化（如统一编码格式）时，写进工具描述，并在工具返回中明确告知模型；否则“智能修正”只会制造模型无法自行诊断的系统性故障
