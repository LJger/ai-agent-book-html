上下文窗口是一台只有一半的检索引擎

检索：非常强

你问什么，注意力就能从成千上万个 token 里把相关的原始记录捞出来——RAG 内置进了每一次前向传播

提炼层：没有

不会被自动数一遍、建索引、就地总结；任何结论每次都要从原始记录里现算

规定每个商家不超过 3 次；“已经打了几次”散落在原始通话记录里——每次决策都要花思考 token 扫描、重新统计，经常数不清，又打了第 4 次

在每次调用结果里直接标明“本次是第 3 次呼叫该商家”：模型立即发现已达到限制，错误率大幅降低

本质：把分散在上下文各处的隐式状态，提炼为可直接使用的显式知识——用极低的额外 token，呈现原本要扫描数千个 token 才能得到的信息

第二章 ·「Agent 状态栏在上下文中的具体位置」· 图2-15

状态会变：每轮替换 vs 持久追加

实现一：每轮替换上下文里只有一份、永远最新的状态

移除旧状态 → 它之后的缓存失效；但它在末尾，失效只覆盖上次注入后新增的那一轮

实现二：持久追加Claude Code 的 <system-reminder> 采用这种方式

只追加、不修改：对缓存完全友好；代价是陈旧状态累积，模型要自己找“最新一条”

第 1 轮缓存命中 失效重算 本轮新增 陈旧状态
第二章 ·「状态更新的两种实现与缓存代价」

取舍：一个粗略的成本模型

S 每条状态
R 两次更新间的新后缀
N 预计更新次数
α 缓存输入相对单价
C替换 ≈ (N−1)(1−α)RC追加 ≈ αSN(N−1)/2αSN/2 < (1−α)R → 倾向实现二
实现一：每轮替换
实现二：持久追加

未计上下文占用和陈旧状态带来的歧义；实际选择还应结合服务商的缓存计费与实测命中率

状态很小、两次更新间消息很多、会话长度受控→ 实现二：保留旧状态比反复重算长后缀便宜
状态较大、更新频繁或轨迹很长→ 实现一：只失效短后缀，避免陈旧状态累积
