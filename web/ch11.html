模型与 Agent 的
共同演进

两朵乌云都不是靠某一次模型升级就能凭空吹散的
模型和 Agent，从来不是上下游，而是一起往前走的。

一个自我强化的飞轮

飞轮第 1 圈越转越快
①用户提出真实的难题
②应用层用 harness 补上模型暂时做不好的事
③补救变成训练信号Agent 在真实业务里替模型趟坑
④下一代模型内化约束对应的代码可以删掉
harness 里层层叠叠的兜底逻辑示意
# 多级上下文压缩
if tokens > L1: ctx = summarize(ctx)
if tokens > L2: ctx = drop_oldest(ctx)
已内化 · 删除
# 失败数千次才熔断的重试

    if step(): break
已内化 · 删除
# 悲观地默认“不安全”的权限判断
def allowed(cmd):
    return cmd in WHITELIST
已内化 · 删除

每一段看似丑陋的“屎山”，记录的都是模型此刻还做不稳的地方

模型之所以能内化，正是因为 Agent 早已在真实业务里替它把这些坑趟了一遍，沉淀成了下一轮训练的信号

后记 ·「模型与 Agent 的共同演进」第 1 段

模型会不会最终吃掉 Harness？

能力前沿 · 模型最做不稳的地方
模型第 1 代每一代稳定内化一种能力
Harness 层数5被吃掉一层，前沿又长出一层
示意
本书的观点

会，但不是一次性吃掉，而是一层一层地吃，并且没有吃完的那一天。

例子：第六章的交互模型

打断、插话这些曾经要靠外挂 harness 才能拼出的行为，如今被直接做进了模型内部

为什么永远吃不完
一

训练以月计：模型等得起，业务等不起

二

模型无法内化真实业务中所有的约束与偏好，总有一层最新的边界需要外部逻辑兜底

三

每一代模型都会打开新的能力前沿，而前沿处恰恰是模型最做不稳的地方

Harness 不会消失，只是随着模型不断向新的前沿迁移。《苦涩的教训》在 Agent 时代的读法：通用方法终将胜出，但“终将”二字里的每一段路，都是 Harness 铺出来的
